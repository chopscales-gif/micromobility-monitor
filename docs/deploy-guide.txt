MICROMOBILITY MONITOR
Deploy guide

This is a demonstration build. Every operator, vehicle, trip and invoice in it is
simulated, the operators are fictional, and the software is not used by, or affiliated
with, any city. This guide says what has been run and what has not.


1. What runs

Four processes and one database:

  Database     PostgreSQL 17 with PostGIS 3.5.
  Simulator    Serves the three fictional operators' GBFS and MDS feeds. Port 4010.
  Worker       Polls the feeds, checks them, judges the rules, builds invoices and
               reports, deletes ride paths past retention. Long-running.
  Web          The Next.js application: staff console, operator portal and public
               open-data page. Port 3000.
  Setup        Runs once: creates the tables and seeds a month of history.

The worker must run all the time. A host that only runs code when a web request
arrives cannot carry it. The hosted copy (section 5) therefore runs without one: it
shows a recorded history with the clock stopped, and nothing new arrives.


2. Run it on your own machine (tested)

This is how the demonstration was built and tested. Needs Node 22 and Docker.

  cp .env.example .env
  Set TOKEN_ENCRYPTION_KEY in .env to the output of: openssl rand -hex 32
  npm install
  npm run db:up            PostGIS in Docker, on port 54329
  npm run db:migrate
  npm run dev:simulator    terminal 1
  npm run db:seed          one month of history, about 400 MB, 2 to 3 minutes
  npm run dev:worker       terminal 2
  npm run dev:web          terminal 3, then open http://localhost:3000

To reset the demo after trying the forms, without rebuilding the history:

  npm run db:seed -- --violations

That rebuilds the cases, findings, alerts and outbox in a few seconds. It does not
undo a new fee schedule, a new or retired zone, a changed rule or an issued invoice.
For those, start the web application with DEMO_RESET=1 and use "Reset it now" in the
strip at the top of the console (section 4), or drop the database volume and seed again.


3. Run it with one command (written, not yet run)

  npm run demo

This is Docker Compose: database, simulator, setup, worker and web, with the web on
http://localhost:3000. The Dockerfile and docker-compose.yml are in the repository,
but the image was never built on the development machine, which did not have the
disk space. Treat the first run as a test. Allow about 3 GB of disk for the image
and the database, and 2 to 3 minutes for the first start while the history is seeded.

The compose file carries a placeholder token key and a local database password.
They are for a local demonstration only.


4. Settings

  DATABASE_URL            Required. The PostgreSQL connection string.
  TOKEN_ENCRYPTION_KEY    Required. 64 hexadecimal characters. Encrypts the
                          operators' feed tokens. Keep it out of the repository.
                          Changing it makes the stored tokens unreadable.
  SIMULATOR_URL           Where the worker finds the simulator, and the address the
                          seed registers for each operator's feeds.
  SIMULATOR_INPROCESS     Set to 1 on the worker to answer the operators' feeds
                          inside the worker itself. The simulator process is then
                          not needed. The feeds are the same ones, built by the
                          same code, still checked for the operator's token; only
                          the network hop is skipped. Unset by default.
  DEMO_RESET              Set to 1 for a copy that strangers share. On the worker
                          it puts the demonstration back as it was seeded every
                          night at 10:00 UTC (3 or 4 in the morning in Salt Lake
                          City). On the web application it adds a line to the
                          strip at the top of the console, saying that other
                          visitors see what is changed, with a "Reset it now"
                          control any seat can use. Unset by default: without it
                          nothing can clear the audit log.
  SIMULATOR_PUBLIC_URL    The simulator's own address, as it should appear in the
                          feed links it publishes.
  DEMO_CLOCK              For a copy with no worker. An instant such as
                          2026-11-10T21:10:00Z. The seed ends its history there,
                          and the web application treats that instant as the
                          present on every screen and in every record it writes.
                          Seed and web application must be given the same value.
                          Never set it where the worker runs. Unset by default.
  CRON_SECRET             For a copy with no worker. The secret the host's
                          scheduler sends to /api/cron/reset, which does the
                          nightly reset in the worker's place. Any other caller
                          gets "not found".
  DATABASE_SSL            Unset locally. Set to require, or verify-full, for any
                          database reached over a network.
  DATABASE_URL_UNPOOLED   Optional. Where a host gives both a pooled and a direct
                          address, the web application uses this direct one. The
                          reset holds a lock for one session, which a pooler
                          that shares sessions between requests would break.
  DATABASE_POOL_MAX,      Optional, web application only. Connections kept per
  DATABASE_IDLE_SECONDS   server process (default 5), and seconds before an idle
                          one is closed (default never).
  ROUTE_RETENTION_DAYS    Days a ride's path is kept. Default 90.
  SEED_IF_EMPTY           Set to 1 to make the seed do nothing on a database that
                          already has history. Used by the setup step.
  SEED_MONTHS, SIM_SEED,  Optional. Months of history to seed, the seed for the
  HEALTH_HISTORY_DAYS     simulated city, and days of feed health history to seed.
  PORT                    The port each process listens on.


5. The hosted copy (done, with limits)

A hosted copy exists at https://micromobility-monitor.vercel.app. It was deployed
and checked on 23 November 2026. It costs nothing to run.

  What it is. The web application alone, on Vercel (Hobby plan), with a Neon
  PostgreSQL 18 database with PostGIS 3.6 (free plan, added through Vercel's
  marketplace as micromobility-monitor-db). No worker and no simulator run.

  What it does not do. It does not poll feeds, judge rules as time passes, build
  new invoices or send the monthly report email. The history was seeded once and
  ends on Tuesday 10 November 2026 at 2:10 in the afternoon, Salt Lake City time.
  The clock is stopped there (DEMO_CLOCK): "now", "the last 24 hours", deadlines
  and the open month are all counted from that moment, and anything a visitor
  records is stamped with it. The strip at the top of every page says so. The
  page called "Live map" shows the fleet as it stood at that moment.

  What still works. Every seat and screen, the map and its 24-hour replay, the
  case, zone, rule and fee forms, issuing an invoice, the PDF and CSV downloads,
  the audit log and the public open-data page.

  Reset. DEMO_RESET=1 is set. "Reset it now" was pressed on the hosted copy after
  changing things and put them back in 6 to 8 seconds. In place of the worker's
  nightly job, Vercel's scheduler calls /api/cron/reset once a day at about
  10:00 UTC (apps/web/vercel.json). The route was called by hand with its secret
  and worked; the first scheduled run had not happened when this was written.

  Ride paths are not stored. The free database allows about 500 MB. After seeding,
  the path of every ride was removed from the hosted database, which brought it
  to 238 MB. No screen draws a ride's path; start and end areas, distance and
  duration are kept. The open-data page still describes the 90-day retention the
  full system applies. With no worker the database does not grow, apart from the
  audit log between resets.

  How it was put there, so it can be repeated:

    1. Create the Vercel project and set its root directory to apps/web. The
       install command in apps/web/vercel.json installs the whole workspace.
    2. Add the database: vercel integration add neon --name micromobility-monitor-db
    3. Seed a local database with DEMO_CLOCK and TOKEN_ENCRYPTION_KEY set
       (npm run db:migrate, npm run db:seed), run
       update trips set route = null, then vacuum full.
    4. Copy it across with pg_dump --no-owner --no-acl piped into psql.
    5. Set on the Vercel project, for production: DEMO_CLOCK and
       TOKEN_ENCRYPTION_KEY (the same two values used to seed), DEMO_RESET=1,
       DATABASE_SSL=require, DATABASE_POOL_MAX=3, DATABASE_IDLE_SECONDS=20 and
       CRON_SECRET (openssl rand -hex 24).
    6. vercel deploy --prod

  Not checked: the maps in an ordinary browser on a phone (they were checked in
  headless Chrome with software rendering, at 1440 and 390 wide), drawing a new
  zone on the hosted map, and behaviour with many visitors at once. The free
  database allows about 100 connections and each server process keeps at most 3.


5a. A copy that keeps running (not done)

The full system, with live polling, has not been hosted. What it needs:

  A host that keeps long-running processes. The simplest fit is one small virtual
  machine with Docker, running the compose file behind a proxy that provides HTTPS
  (Caddy or similar). A container platform with a managed PostgreSQL also fits if
  it offers PostGIS and always-on workers.

  Two processes, not three. With SIMULATOR_INPROCESS=1 the worker answers the
  operators' feeds itself and the simulator process can be left out. Tested on the
  development machine: with the simulator stopped, every feed request in the
  following minutes was answered. Not tested on a host.

  The forms are live. Anyone who opens a public copy can adopt a fee schedule,
  retire a zone, change a rule or close a case, and the next visitor sees the
  result. Set DEMO_RESET=1 on the worker and the web application before sharing a
  public link (the hosted copy has it). What the reset does: removes zones that were added and restores
  ones that were retired, re-adopts the rules, removes fee schedules added since
  the seed, returns the invoices to how they were seeded, rebuilds the cases,
  findings, alerts and outbox, and empties the audit log. It takes about four
  seconds on the seeded month locally, and 6 to 8 on the hosted copy. Its limits:

    Between resets, visitors still see one another's changes.

    A reset pressed by one visitor interrupts any other visitor who is part way
    through a case. The control cannot be used twice within a minute.

    For those few seconds the case list is part built.

    Rides recorded while a visitor's zone existed, or while a seeded zone was
    retired, keep the zone flags they were given at the time.

    Alerts and mail the worker wrote from live feeds since the seed (a feed that
    dropped this morning, say) are cleared and are not written again.

    Case numbers are stable from one reset to the next on the same day, but shift
    as new weeks of history arrive on a copy left running.

  Replace the placeholder key and the database password. Set DATABASE_SSL. Serve
  the site over HTTPS only: the application sends Strict-Transport-Security and
  marks its cookie Secure in production, but does not terminate HTTPS itself.

  Size: the seeded month is about 400 MB, and the database grows as the worker
  keeps polling. Ride paths are deleted after ROUTE_RETENTION_DAYS; trip records
  and feed checks are not trimmed in this build.


6. For a real city program (not done)

A production deployment is a separate piece of work. At the least: connect single
sign-on (docs/data-privacy-and-security.txt, section 6), register the real
operators' feed addresses and tokens in place of the simulator, connect a mail
service in place of the outbox, set the retention periods the city's records
schedule requires, ship the audit log to write-once storage, and have the system
independently reviewed.
